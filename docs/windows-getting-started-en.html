BlinkGTK for Windows — Getting started

Each figure carries the date it was measured. The package sizes and the
number of bundled documents are measured on the ZIP we ship (measured 2026-09-27).
Note: We do not state when the ZIP was built, because that changes every time
it is rebuilt. For the exact byte count and hash of each ZIP, see
<package name>.verify.json (size / sha256) and SHA256SUMS (hashes only),
published alongside the packages. This release was checked on Windows 11 Pro
build 26200 on 2026-09-27 (the extract-and-run check of the package).

BlinkGTK, running on Windows. It follows the same versioning as the Linux build
(Chromium version plus BlinkGTK patch level).
This release, 1.2.3-build3, has the same version number as Linux 1.2.3-build3;
both are Chromium 154.0.8037.57.

The public API matches Linux 1.2.3-build3 except for one entry point.
However, the 51 entry points new to the Windows build in this release (added in Linux 1.2.2 and 1.2.3)
have not yet been called on Windows. We have called 64 of the 152 public entry points on Windows
(§0 of the bundled docs\api-windows-notes-en.md), all of them ones that were already there in the previous release.

How this is counted: an entry point counts as public API when it is both declared
in the public header and exported from the shared library (.so / .dll). The header
declarations include the two _get_type functions that G_DECLARE_FINAL_TYPE declares
(BlinkWebView and BlinkDownload). By that definition Linux has 153 and Windows has 152.

How this was measured (both 2026-09-27): for Linux, the header from the upstream
1.2.3-build3 devel package and the .so from its runtime package, read with nm -D:
the intersection of 154 header declarations and the 189 exports whose names start with
blink_ = 153. For Windows, the intersection of 153 public header declarations in
this release and the 163 DLL exports (dumpbin /exports) whose names start with blink_
= 152. The name filter only leaves out internal
symbols that the header does not declare, so it does not change the intersection.
The Windows header figure of 153 leaves out blink_web_view_attach_to_external_surface
(inside #ifndef _WIN32) and includes blink_gtk_sandbox_init. §0 of the bundled
docs\api-windows-notes-en.md counts the declarations marked BLINKGTK_EXPORT instead
(which include the former and not the latter), so its 153 is a different set;
the intersection of 152 is the same.
Note: with the counting method otherwise the same on both platforms, only the conditional-compilation handling is
mirrored — on Windows we drop what is inside #ifndef _WIN32, on Linux what is
inside #ifdef _WIN32, so that declarations invisible to that platform's users
are not counted.

Missing on Windows blink_web_view_attach_to_external_surface (Wayland-specific)
Only on Windows none

One more entry point sits outside those counts.
blink_gtk_sandbox_init() is declared in the header on both platforms, but neither
shared library exports it. On Windows it is linked into your executable through the
static library blinkgtk_sandbox.lib (shipped in the devel ZIP).
You cannot call it on Linux (see below).

About the two sandbox entry points (measured 2026-09-27; exports were checked with nm -D for the Linux .so and dumpbin /exports for the Windows DLL):

Linux 1.2.3-build3 This Windows build
Declared in the header yes (both) yes (both)
blink_gtk_init_with_sandbox() in the shared library yes yes
blink_gtk_sandbox_init() available no yes (through the static library blinkgtk_sandbox.lib, shipped in the devel ZIP)

blink_gtk_sandbox_init() is Windows-only and cannot be called on Linux.
The header marks it "Windows only." and says of Linux:
"The Linux shared library does not export it, so calling it there fails to link."
On Linux, call blink_gtk_init() or pass NULL to blink_gtk_init_with_sandbox();
code shared between the platforms can guard the call with #ifdef G_OS_WIN32
(per the same header note). The same header names the Windows source as
lib/blinkgtk_sandbox.lib in the BlinkGTK for Windows devel ZIP, from 1.2.1-build3.
Since: is 1.2.1 for blink_gtk_sandbox_init() and 1.2.2 for
blink_gtk_init_with_sandbox(). This note reads the same in the Linux 1.2.3-build3
devel header and in this release's header (compared 2026-09-27).
(Issue #141, which the note on blink_gtk_init_with_sandbox() cites, is a
question we filed in the upstream repository.)

Getting it running

1. Extract

Put the ZIP anywhere. Administrator rights are not required.

2. A warning may appear the first time

These packages are not code-signed. Microsoft Defender SmartScreen may warn
you when you download the ZIP with a browser and run it. Follow the prompts to
run it anyway.

Signing can be added later, so the packages ship unsigned.

Note: We do not have a screenshot of this yet.
On our development machine we do not fetch the package through a browser, so it
never carries the Mark of the Web. That machine cannot reproduce the warning.
We will add the screenshot, with the exact button labels, once we have run
download-to-launch on a clean Windows install.

3. Run it

Run bin\blinkgtk_browser.exe.
Without an argument it opens https://google.com/ (this needs an Internet
connection). Pass a URL to open that page instead.

cd blinkgtk-1.2.3-build3-windows-x64\bin
blinkgtk_browser.exe
blinkgtk_browser.exe https://example.com/

blinkgtk_browser is a minimal sample that shows only what is needed to embed
BlinkGTK. A console window also opens and shows the program's log.

Requirements

OS Windows 10 (64-bit) or later
CPU x64 (32-bit is not supported)
Disk space ZIP about 464 MiB + about 1,316 MiB extracted. You need both while extracting — about 1.8 GiB in practice (1,780 MiB rounded up; measured 2026-09-27)
GTK4 Bundled. Do not install it separately
Visual C++ runtime DLLs bundled (no need to run the Redistributable installer)

Note: MiB here means 1,048,576 bytes. The GitHub Releases page uses the same
unit and labels it "MB", so the ZIP shows as 464 MB there (checked
2026-09-23 by comparing the API byte counts of a release in another public
repository with its Releases page). Tools that count in 1,000,000-byte units show 487 MB.
The bundled documents use the same unit — all six that print
sizes (INSTALLATION-ja.md, INSTALLATION-en.md,
building-with-blinkgtk-ja.md, portable-app-guide-ja.md, faq-ja.md,
linux-windows-differences-ja.md) state that MB means MiB (checked
mechanically, 2026-09-27).

Do not install GTK4 separately. Windows has two incompatible GTK4 ABIs
(gvsbuild = MSVC ABI, MSYS2 = MinGW ABI). Code built against a different ABI
will not link against the bundled GTK4.
(This is the general rule. We have not actually tried mixing them.)

Note: We verified this on Windows 11 Pro (build 26200). We have not tested
Windows 10.

Note: Handing rendered output to GTK has only one path: software.
The EGL render path itself (blink_web_view_egl.cc, blink_wayland_surface.cc)
is not part of the Windows build: how the receiving surface gets composited is
undesigned, and a DirectComposition-based shape is under consideration.
blink_gtk_ensure_egl_recipient() and friends, exported but not declared in the
public header, remain in blinkgtk.dll to keep the ABI, but return 0 on Windows.

The environment variable BLINKGTK_GPU_MODE is read (checked 2026-09-27 on this release).

  • egl starts Chromium without --disable-gpu and changes the reported path name to "P3".
    An ANGLE window was also created, so Chromium may render with the GPU internally
    (how far it uses the GPU is not measured). Handing the output to GTK stays the same as with software.
  • swiftshader is treated like software on Windows (--disable-gpu is added).

In cmd, quote the assignment, as in set "BLINKGTK_GPU_MODE=egl".
Writing set BLINKGTK_GPU_MODE=egl && … leaves a trailing space in the value, which then does not match egl.

Note: Vertical Japanese layout is not guaranteed to match between the two
platforms.

The vertical-layout changes are not in this Windows build — but they are off by
default on Linux too.
The flag that turns them on, CJKVerticalColumnFragmentation, is one BlinkGTK adds (it is not
a Chromium upstream feature). It has status: "experimental" in
runtime_enabled_features.json5, that is off by default, and the
product code never turns it on.

How this was counted (measured 2026-09-27 on the upstream 1.2.3-build3 tree
and this release's Windows tree): calls to the forcing setter
SetCJKVerticalColumnFragmentation... across the whole upstream tree — zero.
Enabling it on the command line (--enable-blink-features) likewise never appears
in product code (zero under third_party/blinkgtk/).

The flag is enabled when you start with either of these:

  • --enable-blink-features=CJKVerticalColumnFragmentation
  • --enable-experimental-web-platform-features (the Chromium switch that enables all
    status: "experimental" features; Chromium's content/child/runtime_features.cc:576,586)

On Windows, put either one on the executable's command line. Chromium reads its
arguments with GetCommandLineW, so passing argv to blink_gtk_init() from your
application does not reach it.
The vertical layout metrics JS API (window.__blinkgtk.verticalFlowMetrics) needs this flag.
On Windows too, either switch makes the API available, and calling it returns an object
(checked 2026-09-27 with a two-column vertical test page).

What differs when the flag is on: on Linux, conditions at four sites change the layout.
They round up the block size of a block that is a direct child of the multicol container and does not
itself take part in the column split, to a multiple of the column width (600px when column-width is auto);
snap lines that cross a column boundary to the column grid; fix the column height
of a vertical multicol whose column height is not yet determined, and let an orthogonal vertical child take part in the column split
(block_layout_algorithm.cc:1418, 2888, column_layout_algorithm.cc:374 and
fragmentation_utils.cc:357 in the upstream 1.2.3-build3 tree). The three corresponding files in
this Windows build have zero occurrences, so none of them apply. (Upstream calls all four together the
"SNAP 系 4 箇所" (the four SNAP sites), and "column-grid snap" on this page means all four.)
Column splitting and line positions may therefore differ from the Linux build.

Line breaking comes from the same source on both platforms (compared by md5, 2026-09-27).
Of the 275 .cc / .h files directly under Blink's core/layout/inline,
platform/fonts/shaping and platform/text, two differ: one only in comments, the other only
in diagnostic output that appears when a development environment variable is set (Linux only).
runtime_enabled_features.json5 is identical too. The line-breaking difference we listed for
the earlier release (Windows on Chromium 152) does not apply to this one.

Note: We have not compared rendered output (screenshots) from the two platforms side by side.
What we checked is the difference in the sources; how much the rendering differs on screen
is not measured. Differences outside the source, such as fonts, have not been compared either,
nor whether the values the layout metrics API returns match Linux.

See §2-b (the vertical layout metrics API) of the bundled
docs\environment-variables-ja.md.

If you are embedding it

The devel ZIP carries the public API headers and the import libraries.

Building also needs Visual Studio Build Tools and the Windows SDK
(we checked with Visual Studio Build Tools 2026).
(Not having to install anything else, including GTK4, applies only to running it.)
Your own compile needs /MD /DCOMPONENT_BUILD.
For the libraries to link and the rest of the build steps, see the bundled docs\building-with-blinkgtk-ja.md (Japanese only).
If you use MSVC on Japanese Windows, also compile with /utf-8.
Without it, the headers are read as code page 932, and the UTF-8 Japanese comments in
the public headers and symbols such as © in the GTK headers raise warning C4819.

The GTK4 development files are bundled because the public header blink_gtk.h
does #include <gtk/gtk.h>.

Three things to know when you embed it (the first is Windows-specific).

  1. Once you include the header, do not also write your own forward
    declarations for the public API     (Windows-specific). The header declares
    them with __declspec(dllimport), so a declaration without it in the same
    translation unit makes clang warn (-Winconsistent-dllimport if the header
    comes first, -Wdll-attribute-on-redeclaration if yours does). With warnings
    treated as errors (-Werror / /WX) the build stops (we have not checked
    how MSVC's cl.exe reports it). Use the header alone.

  2. Free a returned string the caller owns with g_free() —
    blink_handoff_meta_serialize() is the example. The implementation
    allocates with g_strdup_printf(), so the contract is g_free().

    The API reference and its example said free() up to 1.2.3-build1, and
    1.2.3-build2 changed them, and the header, to g_free() (#130). This does not mean free()
    breaks in the current configuration — on Windows blinkgtk.dll and
    glib-2.0-0.dll both use the CRT from DLLs (UCRT) (checked on this release
    with dumpbin /dependents, 2026-09-27). We align it for the contract.

  3. blink_gtk_sandbox_init() is not exported from the DLL. It is linked
    into your executable through the static library blinkgtk_sandbox.lib,
    which the devel ZIP carries. This entry point is Windows-only and cannot
    be called on Linux     (the Linux shared library does not export it; for what to
    call on Linux instead, see the sandbox paragraph above). The background is
    issue #141 in the upstream repository, filed by us.

Reading the version

1.2.3-build3 is the same version number as BlinkGTK itself, tied to the
Chromium version and the BlinkGTK patch level. This one is Chromium
154.0.8037.57.

You can ask the binary in your hands:

> blinkgtk_browser.exe --version
BlinkGTK 1.2.3-build3 (Chromium 154.0.8037.57)

Trust what your copy prints, not the number on this page.
