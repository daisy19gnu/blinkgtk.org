BlinkGTK 1.1.0-build6 Release Notes

Date: 2026-07-29
Chromium: 150.0.7871.46 (stable)
Status: Development build (1.1.0-dev). This distribution includes verification use.

What you can do with this release

Changing the font size no longer blanks the page

Enlarging the font size could leave the page permanently blank. It happened most often
in two-page vertical layouts, and it meant a reading application with a font-size control
could not be built at all.

During a large reflow, the damaged region was computed as empty, which left a blank tile
marked valid and pinned it there. We traced this to its root cause and fixed it, and the
build now carries a regression test that deliberately injects the fault to prove the fix
still holds (Issue #120).

Idle no longer costs a CPU core

Sitting idle used to burn close to one CPU core continuously. That is now gone, so
BlinkGTK is usable on battery-powered devices and on machines left running — kiosks,
signage, embedded panels (Issue #115).

Multi-column layout works in Japanese vertical writing

When column-count was combined with writing-mode: vertical-rl, lines that straddled a
column boundary were dropped from the neighbouring column. That is fixed, so vertical-writing
ebooks and newspaper- or magazine-style multi-column pages now lay out correctly.

It is off by default, so existing rendering does not change. Turn it on at startup:

myapp --enable-blink-features=CJKVerticalColumnFragmentation

The current implementation assumes a 600px column width, column-gap: 0, and zero
border/padding on the orthogonal root. Layouts outside that range render as before
(Issue #110).

Your application decides on permission requests

Permission requests from the page — geolocation, notifications, and so on — are now handed
to your application, which answers allow or deny. The default is deny: if you do not
connect the signal, every request is refused automatically.

That makes the behaviour guaranteeable for kiosks and ebook readers, where you either want
no permission dialogs at all or want only specific requests to succeed.

static gboolean on_permission(BlinkWebView *view,
                              BlinkPermissionRequest *req,
                              gpointer user_data) {
    const char *kind = blink_permission_request_get_type_name(req);
    if (g_strcmp0(kind, "notifications") == 0)
        blink_permission_request_allow(req);   /* allow notifications only */
    else
        blink_permission_request_deny(req);
    return TRUE;   /* handled */
}

g_signal_connect(view, "permission-request", G_CALLBACK(on_permission), NULL);

You can set the User-Agent and cookies

blink_web_view_set_user_agent() overrides the User-Agent and
blink_web_view_set_cookie() installs a cookie. Useful for building a dedicated client for
one service, or for starting up already authenticated.

You can write against it from Python and JavaScript

GObject Introspection support is now in place. The enumerations (LoadEvent, LoadError,
GpuMode, ContentPolicy) are registered as GTypes, property changes emit notify::, and
uri-changed fires on real navigations. Verified from PyGObject and GJS.

Mouse interaction is good enough for a real application

Wheel-scroll coordinates, scrollbar thumb dragging, and clicking after a page transition all
work now. Previously anything away from the centre of the screen would not scroll, and after
switching books clicks stopped working until you restarted (Issue #112, #114).

You can put your application wherever you like

blink_gtk_set_resources_path() now applies to every Chromium resource. Previously only the
resource pack still looked next to the executable, so applications with their own directory
layout would not start.

100 lines show you how to embed it

The bundled sample is now a single blinkgtk_browser (105 lines) that does nothing but
display https://google.com/. Run make in examples/ and it builds. The development
browser shipped previously carried a lot of machinery — render-path switching and the like —
that is only useful while working on BlinkGTK itself, which made it a poor example.

One thing differs from plain GTK: the main loop. Call blink_gtk_run_main_loop() rather
than g_application_run() (with the latter the window stays blank). For GTK4 itself, see
https://docs.gtk.org/gtk4/.

What you need to run it

Based on Chromium 150.0.7871.46 (stable).

The distribution is split into three packages, as WebKitGTK is. Install runtime to run an
application, add devel to build one, and add gir to use it from Python or JavaScript.

Contents When you need it
runtime Shared library and the Chromium runtime Running
devel Headers and blinkgtk-0.1.pc Building
gir GObject Introspection typelib Python / GJS

Always link through pkg-config --cflags --libs blinkgtk-0.1. If you hand-write
-lblinkgtk on its own, the program builds and starts but the page stays blank — Chromium's
allocator shim has to be a direct dependency of the executable.

The shared library SONAME is versioned as libblinkgtk-0.1.so.0. Each release ships
third-party licence notices (THIRD_PARTY_NOTICES.html) and SHA256SUMS.

Switches for isolating a problem

Environment variables that revert to the pre-fix behaviour, in case one of the above causes
trouble for you. You should not normally need any of them.

Variable Reverts
BLINKGTK_120_INVAL_FALLBACK=0 The blank-page fix (damage-region fallback)
BLINKGTK_120_ACT_REDRAW=0 The blank-page fix (redraw supply)
BLINKGTK_CAPTURE_DAMAGE_GATE=0 The capture-throttling half of the idle-CPU fix
BLINKGTK_PUMP_LEGACY=1 The main-loop half of the idle-CPU fix
BLINKGTK_PUMP_RESCUE=0 The main-loop wake-up heartbeat
BLINKGTK_EGL_FRACTIONAL=1 Enables experimental fractional scaling (integer by default, Issue #117)

The supported variables are listed in the bundled api-reference/environment-variables-en.md. Anything not
listed there is for internal diagnostics and may change without notice.

Fixes

Everything not covered above, broken down by build.

build6

Bundled documentation only; the binaries are unchanged.

  • The build command shown in the documentation (gcc ... -lblinkgtk) failed if you ran it as
    written. Corrected in 10 files, 16 places. A gate that actually executes the build commands
    found in the documentation has been added.
  • "Fully compatible with WebKitGTK" was wrong: both the function names and the target objects
    differ. Reworded to match reality.
  • Version references still reading v0.9.x have been updated.
  • Internal development identifiers (CP and Build numbers) removed from user-facing text.
  • Fixed documentation cross-links that did not open on the web.
  • Reorganised pages that led with long explanations before reaching the steps, so the steps
    come first and the reasoning follows.

build5

  • Fixed blink_gtk_set_resources_path() not applying to the resource pack. Placing the
    executable away from the resources failed with
    Check failed: data_pack->LoadFromPath(path).
  • Fixed the build machine's absolute path being embedded as rpath in the bundled sample.
  • Replaced the bundled sample with blinkgtk_browser.
  • Removed command-line option examples from the settings API documentation that the bundled
    sample does not accept, replacing them with API examples.

build4

The documentation bundled with build2 and build3 described 20 APIs that did not exist in the
bundled binaries. Code written as documented would not build. Affected: settings-api,
c-api-reference, navigation-api, signals-api, and the tutorials.

  • Corrected names that disagreed with the implementation
    (blink_web_view_set_enable_javascript → blink_web_view_set_javascript_enabled,
    blink_web_view_set_auto_load_images → blink_web_view_set_images_enabled).
  • Implemented User-Agent, cookies, and permission requests.
  • Withdrew documentation for things that do not exist (the INI-file settings API, the
    accessibility API). They will return once implemented.
  • Added a gate that extracts the distribution itself and machine-checks the shipped
    documentation against the shipped binaries. It is now a precondition for publishing.
  • Stopped shipping unmaintained check programs (api_check.c, api_tester.c).
  • Replaced examples/Makefile with a pkg-config-based one; the previous file was generated by
    autotools and contained absolute paths from the build machine.
  • Regenerated tarball, RPM, and DEB all as build4 (build3 replaced the RPMs only).

build2 (first public release of the v1.1 series, 2026-07-21)

build1 was internal verification only and was not published.

  • Moved to Chromium 150 (stable). V8 snapshot consistency, render smoke tests, and vertical
    writing on real hardware (including the EGL path) verified.
  • Versioned the shared library SONAME as libblinkgtk-0.1.so.0.
  • Started the three-way runtime / devel / gir split.
  • Added a 100ms wake-up heartbeat to the main loop, bounding the delay of queued work
    (measured idle cost: under 0.5%).
  • Added the list of supported environment variables (environment-variables-{ja,en}.md) to the
    bundled documentation.
  • Diagnostic machinery (frame inspection, fault injection) ships disabled behind environment
    variables and does not affect normal operation.

Compatibility

  • Consumers must link the PartitionAlloc allocator shim directly (the bundled pkg-config
    blinkgtk-0.1.pc handles this; Issue #90).
  • No breaking changes to the C API.
  • With the versioned SONAME (libblinkgtk-0.1.so.0), newly-linked consumers get a versioned
    dependency; building via the devel package's pkg-config resolves it automatically.

Known Limitations

  • CJKVerticalColumnFragmentation is a staged implementation assuming column-width 600px /
    column-gap 0 / orthogonal-root border-padding 0 (experimental, off by default).
  • For tarball (FHS) runs, resolve the private dir (/usr/lib64/blinkgtk-0.1/) via the runtime
    ld.so.conf.d fragment or LD_LIBRARY_PATH.
  • Idle CPU consumption (Issue #115) is under continued investigation.
