BlinkGTK 1.2.1-build3 リリースノート

リリース日: 2026-09-08 / Chromium: 152.0.7977.64 / 言語: 日本語 | English

レンダリングエンジンを Chromium 152 に更新しました。前版 (1.2.0) の
Chromium 151 から、上流 1 世代ぶんの改善が入ります。

build3 でできるようになったこと

不具合を報告するときに、どの版で起きたかが実行時に分かるようになりました

これまで、実行時に版を問い合わせると 1.2.1 としか返らず、build 番号が
取れませんでした。同じ版でも build が違えば挙動が違うことがあります。実際に
v1.2.0 の build2 と build3 では EGL の既定経路が違います。それを API で
区別できず、外部の利用者はパッケージのファイル名から版を読むしか
ありませんでした。当方の不備です。

build 番号を返す口を追加しました。

const char* full = blink_gtk_get_version_full();  /* "1.2.1-build3" */
const char* b    = blink_gtk_get_build();         /* "3"。不明なら NULL */

blink_gtk_get_version_full() は必ず非 NULLです。不具合を報告する際は、
これ 1 つを貼れば版が一意に決まります。blink_gtk_get_version() の戻り値は
従来どおり 1.2.1 で、既存の呼び出しの動作は変わりません。

blink_gtk_get_build() は、build 番号が分からない場合に NULL を返します。
"0" や "unknown" は返しません。build 番号と読めてしまうためです。

画面が出ないときに、ログだけで原因を切り分けられるようになりました

EGL 経路で描画データを配る箇所には 3 通りの分岐があり、そのうち 1 つは
画面に貼らずに破棄します (表示は GTK 側が行います)。ところがログは、
どの分岐を通っても「attach」と出ていました。何をしたのか分からない計器でした。

実際に呼んだ操作を書くようにしました。

[CP-947 goal-3 deliver] dmabuf #1: op=attach+viewport wl_buffer=80 1280x553 ...
[CP-947 goal-3 deliver] dmabuf #1: op=destroy wl_buffer=77 1280x553 ...

(この 2 行は設定の異なる 2 つの実行から 1 行ずつ並べたものです。
1 つの実行で #1 が 2 回出ることはありません)

wl_buffer= は Wayland の wire id です。WAYLAND_DEBUG=1 で採った protocol log
と行を突き合わせられます。

あわせて、これまで先頭数枚で打ち切っていた 2 つの計器を、必要なときだけ
伸ばせるようにしました。既定の枚数は変えていません。

変数 意味
BLINKGTK_DELIVER_LOG_MAX 配送ログの行数上限 (既定 5)
BLINKGTK_CONTENT_PROBE_MAX 中身があるかの検査を続ける枚数 (既定 8)

BLINKGTK_CONTENT_PROBE_MAX は表示の挙動を変えません。測る枚数だけを
増やします。定常状態 (9 枚目以降) が空かどうかを外から確かめられます。

検査の結果を表す語も改めました。これまで空のフレームを SKIP と記録して
いましたが、SKIP は動作の名 (このフレームの表示を見送る) であって
測定結果の名ではありません。読んだ人が「計測の上限に達したから見送った」と
実際に取り違えました。当方も返信で同じ誤りを説明しています。
BLANK (測って空だった) に改めました。

描画経路の切り替えに EGL が加わりました

アプリケーションから描画経路を切り替える blink_web_view_switch_render_path()
に、EGL 経路が加わりました。EGL で起動していれば、再起動せずに
ソフトウェア描画との間を往復できます。

制約があります。 往復できるのは BLINKGTK_GPU_MODE=egl で起動した
場合だけです。ソフトウェア描画で起動したプロセスは EGL へ移れません。
合成モードは上流でプロセス全体の一方通行で、software 起動では GPU 側の
描画データがそもそも作られないためです。

追加の設定は要りません。 BLINKGTK_KEEP_GPU_COMPOSITING は
software 起動のときだけ読まれる設定で、EGL 起動では何もしません。

50 往復 (切り替え 100 回) を続ける試験では、100 回の切り替えすべてが
成功し、ファイル記述子は増えませんでした。メモリは切り替え 1 回あたり
中央値 16 KB の積み上がりがあります。「漏れが無い」とは言えません。 測ったのは開発機での headless 環境・静止ページ・単一プロセスまでで、
実機では測っていません。

直したこと

  • 診断用の環境変数に =0 を指定しても止まらないものがありました。
    否定の解釈をそろえて解消しました

build2 でできるようになったこと

GPU が使用できない環境でも、フォールバックによりソフトウェア描画で表示されるようになりました

BLINKGTK_GPU_MODE=egl を指定した環境で GPU 経路が利用できない場合
(ドライバが無い、仮想環境で GPU が見えない、など)、ソフトウェア描画へ
フォールバックして表示を継続します。

描画データが 5 秒間 1 枚も届かなければ切り替わり、その理由を標準エラー出力に
記します。

[BlinkGTK] EGL 経路に dmabuf が 5000 ms 経っても 1 枚も届きません。
この機械では GPU 経路が使えない可能性があります。画面が白いままにならないよう
software 経路へ退避します (無効化: BLINKGTK_EGL_AUTO_FALLBACK=0)

GPU が使える機械では切り替わりません。待ち時間は BLINKGTK_EGL_AUTO_FALLBACK_MS
で変えられます。切り替えそのものを止めるには BLINKGTK_EGL_AUTO_FALLBACK=0 を
設定してください (画面は白いままになります)。

画面を撮影した画像の色が入れ替わらなくなりました

blink_web_view_capture_screenshot() で保存した画像で、赤と青が入れ替わる
ことがありました。純粋な赤のページを撮ると純粋な青で保存されます。撮影のたびに
起きたり起きなかったりするため、1 枚だけ見て「直った」と判断できない形でした。

保存経路が画像データのバイト順を確認せずに扱っていたのが原因です。色の形式を
検査して揃えるようにしました。8 枚連続で撮影したときの入れ替わりは 4 枚から
0 枚になります。

追加した環境変数

変数 意味
BLINKGTK_EGL_AUTO_FALLBACK 0 で上記の自動切り替えを止めます (既定は有効)
BLINKGTK_EGL_AUTO_FALLBACK_MS 切り替えまでの待ち時間 (既定 5000 ミリ秒)
BLINKGTK_KEEP_GPU_COMPOSITING 1 で software 起動時も GPU 合成を無効にしません

BLINKGTK_KEEP_GPU_COMPOSITING は描画経路を実行中に切り替えるための前提です。
代わりに CPU 使用量が増えます — 手元の測定 (Intel UHD / Mesa、アニメーション
するページを 20 秒、3 回の中央値) では約 12% 増でした。その機械・そのページでの
比で、上限でも代表値でもありません。このため既定は無効です。詳しくは同梱の環境変数リファレンス (environment-variables-ja.md) を参照してください。

build1 でできるようになったこと

縦組みで行が途中までしか埋まらない現象が直りました

縦書きの段落で、閉じ括弧などの禁則対象が行末に来ると、行が半分ほどで折り返す
ことがありました。34 文字入る行に 17 文字しか入らず、残りが次の行へ送られます。
文字を大きくして読む設定ほど目立ちます。

行が収まらないと判断されたとき、直前の合法な改行位置を試すようにしました。
実測では、同じ段落が 17 文字 + 18 文字の 2 行から、34 文字 + 1 文字へ変わります。

閉じ括弧 7 種すべてで再現していた現象です。。 や 、 では起きません。
上流にも報告しています (crbug 542686223)。

縦組みの段組みで、列が容量まで詰まるようになりました

章の途中の列が最後の 1 行を次の列へ送ってしまう現象がありました。
原因のひとつはエンジン既定のルビ予約で、列の切断幅から 0.5em を控除していました。
16 行入る列では、これがちょうど 1 行を奪います。

この控除の既定を 0 にしました。実測で、容量 16.024 行の列が 4 列とも 16 行に
到達します。従来の挙動に戻す場合は BLINKGTK_RUBY_RESERVE_EM=0.5 を指定してください。

direction: rtl で縦組みの行格子が保たれます

右から左に流す指定と縦組みを組み合わせたとき、列の境界をまたいで文字がはみ出す
ことがありました。切断の寸法を列幅に統一して解消しています。

更新にあたって

実行部分は Chromium 152.0.7977.64 です。前版 (151.0.7922.108) から
ウィンドウ・入力・描画の各経路が上流の変更に追従しています。

組版の結果が変わります。 上記 3 点はいずれも版面に影響します。
既存の文書を開いたときの行数・列の詰まり方が前版と異なる場合があります。
これは不具合の修正によるもので、意図した変更です。

動作を確認した範囲

  • 描画: software / EGL の両経路で、縦組みページが窓を埋めて描画されること
  • 起動と終了: 異常終了なし
  • 組版: 上記 3 点をそれぞれ機械判定で確認
  • パッケージ: 署名、同梱ヘッダの版数、依存名の解決性

測っていないこと: 実機での長時間運用、EGL 経路のリサイズ中の挙動、
描画経路を切り替えながらの連続運用。
