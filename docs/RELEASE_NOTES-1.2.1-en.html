BlinkGTK 1.2.1-build3 Release Notes

Release date: 2026-09-08 / Chromium: 152.0.7977.64 / Language: English | 日本語

The rendering engine has been updated to Chromium 152, one upstream
generation on from Chromium 151 in the previous release (1.2.0).

What build3 makes possible

The exact build is now visible at run time when you report a problem

Until now, asking the library for its version at run time returned only
1.2.1 -- the build number was not available. Behaviour can differ
between builds of one version: in v1.2.0, build2 and build3 use different
default EGL paths. The API could not tell them apart, so external users had
no way to identify a build except by reading the package file name. That
was our omission.

Accessors for the build number have been added.

const char* full = blink_gtk_get_version_full();  /* "1.2.1-build3" */
const char* b    = blink_gtk_get_build();         /* "3", or NULL if unknown */

blink_gtk_get_version_full() is never NULL. Quote this single string in
a bug report and the build is identified. blink_gtk_get_version() still
returns 1.2.1, so existing callers are unaffected.

blink_gtk_get_build() returns NULL when the build number is unknown. It
never returns "0" or "unknown", since those read as build numbers.

Blank-screen causes can now be separated from the log alone

The code that delivers frames on the EGL path has three branches, and one of
them discards the buffer without putting it on screen (GTK displays it
instead). The log said "attach" whichever branch ran. The instrument did not
report what it had done.

It now records the operation actually performed.

[CP-947 goal-3 deliver] dmabuf #1: op=attach+viewport wl_buffer=80 1280x553 ...
[CP-947 goal-3 deliver] dmabuf #1: op=destroy wl_buffer=77 1280x553 ...

(These two lines come from two separate runs with different settings, one
line each. A single run never prints #1 twice.)

wl_buffer= is the Wayland wire id, so these lines can be correlated with a
protocol log captured under WAYLAND_DEBUG=1.

Two instruments that stopped after the first few frames can now be extended
when needed. The defaults are unchanged.

Variable Meaning
BLINKGTK_DELIVER_LOG_MAX Maximum delivery log lines (default 5)
BLINKGTK_CONTENT_PROBE_MAX Frames to keep testing for content (default 8)

BLINKGTK_CONTENT_PROBE_MAX does not change display behaviour; it only
raises how many frames are measured, so you can check from outside whether the
steady state (frame 9 onward) is blank.

The word used for the result has also changed. An empty frame used to be
recorded as SKIP, but SKIP names an action (skip displaying this
frame), not a measurement. Readers did take it to mean "the measurement
cap was reached", and we repeated the same mistake in a reply. It is now
BLANK (measured, and found empty).

The EGL path joined live render-path switching

blink_web_view_switch_render_path() now covers the EGL path. If the
process started under EGL, it can move back and forth to software rendering
without restarting.

There is a limit. Round trips are possible only when the process started
with BLINKGTK_GPU_MODE=egl. A process started under software rendering
cannot move to EGL: upstream treats the compositing mode as one-way for the
whole process, and under a software start no GPU-side frames are produced at
all.

No extra setting is needed. BLINKGTK_KEEP_GPU_COMPOSITING is read only
on a software start; it does nothing when the process starts under EGL.

A soak of 50 round trips (100 swaps) completed all 100 swaps successfully,
with no increase in file descriptors. Memory grew by a median of 16 KB
per swap. This does not amount to "no leak". It was measured on a development
machine in a headless environment, on a static page, for a single process
only; it has not been measured on real hardware.

Fixed

  • Some diagnostic environment variables did not turn off when set to =0.
    The handling of negative values has been aligned

What build2 makes possible

Falls back to software rendering where the GPU path is unavailable

When BLINKGTK_GPU_MODE=egl is selected on a machine where the GPU path cannot be
used (no driver, no GPU visible inside a virtual machine, and so on), BlinkGTK
falls back to software rendering and keeps drawing.

The switch happens when no frame reaches the GPU path within five seconds, and
the reason is written to standard error.
The message is currently emitted in Japanese; it reads: "No frame reached the EGL
path within 5000 ms. The GPU path may not be usable on this machine. Falling back
to the software path so the window does not stay blank (disable with
BLINKGTK_EGL_AUTO_FALLBACK=0)."

The switch does not happen on machines where the GPU path works. Change the wait
with BLINKGTK_EGL_AUTO_FALLBACK_MS, or turn the switch off entirely with
BLINKGTK_EGL_AUTO_FALLBACK=0 (the window then stays blank).

Captured screenshots no longer come out with red and blue swapped

Images saved through blink_web_view_capture_screenshot() could come back with
red and blue exchanged — a pure red page saved as pure blue. It happened on
some captures and not others, so a single image was not enough to tell whether it
was fixed.

The save path handled the image data without checking its byte order. It now
inspects the colour format and converts. Across eight consecutive captures, the
number of swapped images goes from four to zero.

New environment variables

Variable Meaning
BLINKGTK_EGL_AUTO_FALLBACK 0 turns off the automatic switch described above (on by default)
BLINKGTK_EGL_AUTO_FALLBACK_MS How long to wait before switching (default 5000 ms)
BLINKGTK_KEEP_GPU_COMPOSITING 1 keeps GPU compositing enabled even when starting in software

BLINKGTK_KEEP_GPU_COMPOSITING is what allows the rendering path to be switched
while running. In exchange, CPU use goes up — in our measurement (Intel UHD /
Mesa, an animating page, 20 seconds, median of three runs) it was about 12%
higher. That is the ratio for that machine and that page, neither an upper bound
nor a representative value. For this reason the option is off by default. See the bundled environment variable reference (environment-variables-en.md).

What is now possible in build1

Vertical lines no longer break half-way

In vertical writing, a paragraph could wrap about half-way along the line
when a closing bracket fell at the line end. A line with room for 34 characters
held only 17, and the rest moved to the next line. The larger the reading size,
the more visible it was.

When a line is judged not to fit, the engine now tries the preceding legal break
opportunity. Measured on the same paragraph, the result changes from
17 + 18 characters across two lines to 34 + 1.

All seven closing brackets reproduced it; 。 and 、 did not. Reported
upstream as crbug 542686223.

Columns in vertical multi-column layout now fill to capacity

A column in the middle of a chapter could push its last line into the next
column. One cause was the engine's default ruby reservation, which deducted
0.5em from the column's break width. In a column with room for 16 lines, that
deduction costs exactly one line.

The default deduction is now 0. Measured on a synthetic with a capacity of
16.024 lines, all four columns reach 16 lines. To restore the previous
behaviour, set BLINKGTK_RUBY_RESERVE_EM=0.5.

The line grid is preserved with direction: rtl

Combining right-to-left flow with vertical writing could let glyphs cross a
column boundary. The slice dimension is now unified with the column width.

Before you update

The runtime is Chromium 152.0.7977.64. Since the previous release
(151.0.7922.108), the window, input and rendering paths follow upstream changes.

Typeset output changes. All three items above affect the page layout.
Existing documents may show a different number of lines, or fill columns
differently, compared with the previous release. This follows from the fixes
and is intended.

What was verified

  • Rendering: vertical pages fill the window on both the software and EGL paths
  • Startup and shutdown: no abnormal termination
  • Typesetting: each of the three items above checked mechanically
  • Packaging: signature, bundled header version, dependency resolvability

Not measured: long-running use on real hardware, EGL behaviour during
resize, continuous operation while switching render paths.
