BlinkGTK 1.2.7-build4 Release Notes

Release date: 2026-11-24 / Chromium: 158.0.8127.36 / Language: 日本語 | English

build4: Fix for the application crashing when remote debugging is opened

If you use build3 or earlier and your application calls blink_web_view_open_devtools(), please update to build4. The public API is unchanged, so you do not need to rebuild your application. Applications that do not call this function behave the same as in build3.

The remote debugging port now opens — Up to build3, calling blink_web_view_open_devtools() made the application crash on the spot. In build4 the remote debugging port opens on the requested port, and the function returns that port number.

  • From the developer tools of a browser such as Chrome, you can find and connect to the displayed page at http://localhost:<port> (for example http://localhost:9222/json/list).
  • The port accepts connections only from this machine (127.0.0.1). While it is open, other programs on the same machine can also connect, so open it only when you need it. To close it, call blink_web_view_close_devtools().
  • If BLINK_CONTENT_POLICY_NO_DEVTOOLS is set with blink_web_view_set_content_policy(), the port is not opened and the function returns 0, as before.

The Browser field of /json/version shows the version — Up to build3, the Browser field of the remote debugging /json/version (and the product of Browser.getVersion in the DevTools protocol) was empty. In build4 it returns Chrome/<Chromium version> (Chrome/158.0.8127.36 in this release). The User-Agent sent to pages is unchanged.

1.2.5 and 1.2.6 contain the same code and are expected to crash in the same way, but this has not been tested. This was checked by calling the function from a test program and reading /json/version and /json/list. Browser.getVersion has not been tested.

build3: Pages no longer stop on some Web APIs, and fixes for the leave-page confirmation, language, client certificates and dragging

If you use build2 or earlier, please update to build3. The public API is unchanged (only the descriptive comments in the public header changed), so you do not need to rebuild your application.

However, if your application sets a handler with blink_web_view_set_javascript_dialog_handler(), please read "The leave-page confirmation reaches the handler" below. If your handler returns TRUE without checking the dialog type, a change is needed.

Web APIs that no longer make the page crash or stop — Up to build2, pages that call the following APIs stopped working. In build3 each of them reports that it is unavailable, and the page keeps running. Any site can call them, so this concerns applications that show general web pages.

  • Badges (navigator.setAppBadge() / navigator.clearAppBadge()): calling them from a secure page such as an HTTPS page made the page crash. In build3 the call finishes without doing anything (the application does not show a badge). Calls from a Service Worker have not been tested.
  • On-device speech recognition queries (SpeechRecognition.available() with processLocally: true, and SpeechRecognition.install()): the page crashed. In build3 available() returns "unavailable" and install() returns false. BlinkGTK has no on-device speech recognition.
  • Web app installation (navigator.install()): it never returned a result. In build3 it fails right away with AbortError. The <install> element has not been tested.

The leave-page confirmation reaches the handler — When a page asked for a beforeunload confirmation (such as "changes you made may not be saved"), up to build2 the JavaScript dialog handler was not called and the page was always left. In build3 the request reaches the handler with dialog_type = BLINK_JS_DIALOG_BEFORE_UNLOAD. In the response, success = TRUE leaves the page and FALSE stays on it. message is a fixed English text; pages cannot change it. A page asks for this confirmation only after the user has interacted with it.

  • With no handler set, or when the handler returns FALSE for this type, the page is left right away as before (the no-handler case has not been tested; in the code it behaves as before).
  • If the handler returns TRUE but never responds, the navigation does not proceed. If your handler returns TRUE without checking the type, make it handle BLINK_JS_DIALOG_BEFORE_UNLOAD, or return FALSE for this type.

The language sent to servers follows the environment — Up to build2, in any language environment, the language sent to servers (the HTTP Accept-Language header) was en-us,en and navigator.languages was en-US. Sites that change their content by language therefore returned the English version even in a Japanese environment. In build3 the language comes from --lang if it is passed at startup; otherwise it comes from the first of the environment variables LC_ALL, LC_MESSAGES and LANG that has a value.

  • Example: with LANG=ja_JP.UTF-8, Accept-Language is ja-JP,ja;q=0.9,en-US;q=0.8,en;q=0.7 and navigator.languages is ja-JP,ja,en-US,en.
  • With LANG=C, Accept-Language stays en-us,en as before. navigator.languages changes from en-US to en-US,en.
  • If your application expects English pages, what a site returns may now depend on the language environment. To keep English, start the application with LANG=C.

Sites that optionally ask for a client certificate now open — Up to build2, sites that "optionally" ask for a client certificate during the TLS connection failed to load. In build3 the connection continues without sending a certificate, and the page is shown. There is no screen or API for choosing a certificate, and no certificate is sent. Sites that require a certificate have not been tested.

Clicks reach the page after dragging inside it — Up to build2, dragging text, an image or a link inside a page left the page in the middle of a drag, and later clicks did not reach the page. In build3 the drag ends right away as cancelled (the page is told that nothing was dropped), and later clicks reach the page as usual. Drag and drop itself is not supported: you cannot drop inside the page, and files dropped from a file manager are not accepted. This was checked with mouse input sent by a test program.

build2: Old screens are no longer shown, and X11 code is removed

If you use build1, please update to build2. The public API is unchanged, so you do not need to rebuild your application.

Old screens are no longer shown — On the default path for software rendering on a scale-1 display, a frame that does not contain the current page's drawing is now discarded instead of being shown. The screen kept while presentation is stopped (with BLINK_PRESENT_WARM set through blink_web_view_set_presentation_policy(), or while the window is hidden with BLINKGTK_PRESENT_POLICY=warm) is also discarded when presentation resumes if the page has been redrawn since then. This keeps an earlier screen, or a screen without the page in it, from being shown. Displays with a scale other than 1, and GPU rendering, are not affected.

X11 code removed — BlinkGTK on Linux runs on Wayland only. The X11 code it never used has been removed from the library. Usage and appearance are unchanged.

build1: Updated to Chromium 158

BlinkGTK's rendering engine is now Chromium 158.0.8127.36.

Security (Chromium 158)

The Chromium 158 desktop stable release includes 204 upstream security fixes. See the official Chromium announcement for details.

This release is for Linux. If you use an earlier version, update to this release to receive these security fixes.

Rendering and console output

On the default software path, the changed area is passed to GTK and Wayland as the update region. Set BLINKGTK_T2_DAMAGE=0 to restore full-window updates. This reduces the area passed to the compositor for pages with small changes; a reduction in application CPU time has not been demonstrated.

Set BLINKGTK_CONSOLE_STDOUT=0 to suppress page console messages on standard output. Output remains enabled by default, and the BlinkGTK message bridge is unaffected.

Normal Linux startup is Wayland-only. The public API is unchanged.
