BlinkGTK for Windows v1.2.1-build3 released

2026-09-24 · Release

The first BlinkGTK package for Windows is out, produced by BlinkGTK-Windows. There is a ZIP you unpack and run (bin\blinkgtk_browser.exe) and a devel ZIP for embedding BlinkGTK in your application. It targets x64 Windows 10 (64-bit) or later and was verified on Windows 11 Pro. It is based on Chromium 152, a different version from the Linux build (v1.2.3, Chromium 154). Rendering uses the software path only, and the package is not code-signed yet.

v1.2.3-build1 released

2026-09-24 · Release

The rendering engine is updated to Chromium 154.0.8037.57. Settings such as blink_web_view_set_javascript_enabled(FALSE) now take effect on the page. Up to 1.2.2 the value was only stored, and page scripts still ran after passing FALSE. Turning off images and localStorage, and the default font size, also work now. The default encoding does not take effect yet. The input method now follows GTK's choice. To get the 1.2.2 behaviour, set BLINKGTK_IM_MODULE=ibus. A custom-scheme handler can return out_mime with a charset and the page is still shown as HTML, and pages can call fetch() on schemes listed in BLINKGTK_EXTRA_SCHEMES. Packaged builds start without naming the resource directory. These fixes follow reports from an external user. From this release there are also Fedora 45 RPMs (.fc45). They contain the same binaries as the Fedora 44 packages, repackaged on a Fedora 45 machine. The dnf repository is now split by Fedora release. Existing settings keep receiving the Fedora 44 packages. To receive the Fedora 45 packages through dnf, fetch blinkgtk.repo again (sudo curl -o /etc/yum.repos.d/blinkgtk.repo https://blinkgtk.org/repo/fedora/blinkgtk.repo).

From v1.2.4, packages will target Fedora 45 or newer

2026-09-20 · Notice

From v1.2.4 (Chromium 155, upstream stable expected 2026-10-06), the packages we distribute will target Fedora 45 or newer. Fedora 44 will be served up to v1.2.3 (Chromium 154). The reason is that our build machine moves to Fedora 45. BlinkGTK packages link directly against the C library (glibc) of the machine that built them, and glibc compatibility runs one way: what is built on a newer version cannot be loaded on an older one. Fedora 45 ships glibc 2.44 and Fedora 44 ships 2.43, so a package built on Fedora 45 will not install on Fedora 44. If you are on Fedora 44, v1.2.3 stays available and will not be withdrawn. Upgrading to Fedora 45 lets you receive v1.2.4 and later through dnf as usual, with no change to the repository configuration. Packages up to v1.2.3 also run on Fedora 45; we verified this by installing and loading them there (Fedora 45, glibc 2.44, GTK4 4.23.4). Fedora 44 itself is supported until 2027-06-02, so our support ends earlier than that.

v1.2.2-build6 released

2026-09-19 · Release

Each view can now have its own profile and cache. Until now every WebView in a process shared one profile and one cache, so opening the same URL in several views served all but the first from the cache and only one real load took place. Pass a name — blink_web_view_new_with_profile("tab1") — and that view gets its own HTTP cache, cookies, localStorage and IndexedDB. Names may contain letters, digits, - and _ ; the same name means the same profile. A named profile keeps its HTTP cache under profiles/NAME/Cache, so it survives across runs. The default blink_web_view_new() behaves as before. The permission-request signal also now names 40 permission types instead of 13, so the 27 that previously arrived as unknown (screen-wake-lock, local-fonts, persistent-storage, automatic-fullscreen, pointer-lock and others) can be told apart.

v1.2.2-build5 released

2026-09-14 · Release

The rendering path can now be chosen from the API. Call blink_gtk_set_gpu_mode() before blink_gtk_init() and the engine starts on that path. Until now, asking for EGL through blink_web_view_new_with_gpu_mode() did not change the path. The rendering path is settled during engine initialisation, together with the startup flags handed to the GPU process, so it can no longer be changed by the time a WebView is created. The startup log named EGL in both cases, so there was no way to tell from outside whether the request had taken effect. Without also setting BLINKGTK_GPU_MODE, applications asking for EGL were running on the CPU pixel path, which has different performance characteristics from the zero-copy path. After initialisation, blink_web_view_get_gpu_mode() reports the path actually in use, and the startup log names it as well. Reported by an external user. The rendering engine remains Chromium 153.0.8010.36, and typesetting results are unchanged from build4.

v1.2.2-build4 released

2026-09-13 · Release

Fixed a problem where the GPU path (BLINKGTK_GPU_MODE=egl) stayed blank from start to finish on systems using a Virtio GPU, such as virtual machines. To decide whether a frame is empty, the engine reads the drawn image from the CPU side; on this kind of GPU the drawing happens outside the machine, so that read sees nothing, and frames that did have content were judged empty and withheld. Pages without animation were the most affected, staying blank for as long as they were open. A frame that reads as all zeros is no longer treated as empty but as "we cannot tell from here", and display is withheld only when the frame is genuinely white. Assistive technology started after the application now reaches the content as well; until now a screen reader had to be running before launch, so turning one on was too late. The rendering engine remains Chromium 153.0.8010.36.

v1.2.2-build3 released

2026-09-11 · Release

Closing the window before a page finished loading no longer crashes. Opening a book and closing it right away — an ordinary action — triggered it; closing after the page had rendered did not, which made it easy to miss. The cause was ours: while the page container was being torn down, a notification was delivered to a handler that was already looking at something released. The handler is now detached first. The workaround (waiting for the load to finish before closing) is no longer needed. Reported by an external user. This build also adds a diagnostic that asks the compositor whether a frame reached the screen — previously our records ended at "the buffer was submitted", so "the content was empty" and "the content was there but never displayed" could not be told apart. It is printed only with BLINKGTK_GX_LOG=1; nothing changes by default. The rendering engine remains Chromium 153.0.8010.36 and typesetting is unchanged from build2.

v1.2.2-build1 released

2026-09-10 · Release

In vertical writing, a line no longer breaks half-way when a closing bracket falls at the line end. A line with room for 35 characters held only 17, and text-align: justify then doubled the inter-character advance. Of 13 configurations, 8 exhibited it and all are now fixed; it does not occur in horizontal writing. We reported it upstream (crbug 542686223) and Chromium fixed it. The rendering engine is now Chromium 153.0.8010.36. The bundled demo answers --version, so a problem report can identify the build exactly.We measured how many characters fit on one line; we did not measure how much room is left at the end of a column in multi-column layout.

v1.2.2-build2 released

2026-09-10 · Release

Corrects an error in the release notes shipped with build1. They said our previous workaround had been removed; it had not, and it is still present in this release. The wording now matches the artifact. The API reference heading also still read “Target version: BlinkGTK 1.2.1 (Chromium 152.0.7977.64)” from one release back; it now states the actual version. The program is otherwise identical to build1 and typeset output does not change; what changes is the version shown in the bundled documents and the reported version string, now 1.2.2-build2. The error was found through an enquiry from BlinkGTK-Readium.

v1.2.1-build3 released

2026-09-08 · Release

The build number is now available at run time when you report a problem. Until now, asking the library for its version returned only 1.2.1, with no build number. Behaviour can differ between builds of one version, and external users had no way to identify a build except by reading the package file name. blink_gtk_get_version_full() returns 1.2.1-build3; the return value of the existing blink_gtk_get_version() is unchanged. The frame-delivery log now records the operation actually performed and the Wayland buffer id, the measurement caps can be raised, and live render-path switching covers the EGL path (only when started with BLINKGTK_GPU_MODE=egl).

v1.2.1-build2 released

2026-08-30 · Release

Where the GPU path is unavailable — no driver, or no GPU visible inside a virtual machine — BlinkGTK now falls back to software rendering and keeps drawing. It switches when no frame arrives within five seconds and writes the reason to standard error, and it does not switch where the GPU path works. Captured screenshots no longer come out with red and blue exchanged.

2026-08-27 · Release

The rendering engine is updated to Chromium 152. In vertical writing, lines no longer break half-way when a closing bracket falls at the line end (a line with room for 34 characters held only 17), and columns now fill to capacity. The line grid is preserved with direction: rtl. Typeset output changes.

v1.2.0-build9 released

2026-08-16 · Release

Render paths can now be switched live, without restarting the application (the BlinkShift public API). A switch takes a few hundred milliseconds in our test environment and rolls back automatically if the new path fails its render check. Also adds blink_gtk_application_run() for correct GtkApplication integration and a presentation-policy API, and fixes large user scripts never reaching the renderer.

v1.2.0-build8 released

2026-08-12 · Release

Applied the results of a security review. Per-site process isolation is now on by default — the boundary that stops a compromised page reading another site's data. Opening several sites now uses more renderer processes, which can increase memory use. Sandbox availability is now measured rather than inferred, and there is a new API to query the sandbox state. A reference page for environment variables is also published.

v1.2.0-build7 released

2026-08-12 · Release

The header shipped with the development package claimed the previous release (this affects every v1.2.0 build from build1 through build6). The runtime API was always correct, so only compile-time macros were affected. Nothing includes that header, so builds kept succeeding — which is why it went unnoticed for so long. The runtime itself is identical to build6; Chromium was not rebuilt.
